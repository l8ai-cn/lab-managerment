# Experiment Management Module

This document prepares the first implementation slice for an experiment
management business module. It defines the business scope, domain model, state
transitions, API surface, permissions, and implementation checkpoints.

## Goals

- Manage experiments through planning, approval, execution, review, and
  archiving.
- Keep experiment metadata, protocols, samples, records, results, and audit
  history traceable.
- Support controlled collaboration among researchers, reviewers, lab managers,
  and system administrators.
- Provide a stable module boundary that can be implemented independently and
  integrated with inventory, device, user, notification, and reporting modules
  later.

## Non-goals for the First Slice

- Full laboratory inventory lifecycle management.
- Instrument scheduling optimization.
- Electronic signature compliance beyond basic audit traceability.
- Advanced statistical analysis or visualization.
- Cross-tenant billing and cost allocation.

## User Roles

| Role | Responsibilities |
| --- | --- |
| Researcher | Create experiment plans, submit approval requests, maintain execution records, upload results. |
| Reviewer | Review experiment plans and result reports, request changes, approve or reject submissions. |
| Lab Manager | Coordinate laboratory resources, monitor experiment progress, close or archive experiments. |
| Administrator | Configure dictionaries, permissions, templates, and module-level settings. |

## Core Capabilities

1. Experiment creation
   - Basic information: title, objective, category, priority, owner, team,
     planned date range.
   - Protocol information: steps, materials, safety notes, expected outputs.
   - Related resources: samples, equipment, reagents, attachments.
2. Approval workflow
   - Draft plans can be submitted for review.
   - Reviewers can approve, reject, or request changes.
   - Approval comments are retained in the audit trail.
3. Execution tracking
   - Approved experiments can enter execution.
   - Researchers can add daily records, observations, deviations, and
     attachments.
   - Managers can monitor progress and risks.
4. Result management
   - Researchers can submit result summaries, files, metrics, and conclusions.
   - Reviewers can accept results or request rework.
5. Archiving
   - Completed experiments can be archived.
   - Archived records become read-only except for administrative audit metadata.

## Domain Model

| --- | --- |

| code | Human-readable business code, generated by rule. |
| title | Experiment title. |

## Lifecycle Statuses

| Status | Meaning |
| --- | --- |
| draft | Plan is being edited. |
| pending_review | Plan has been submitted for approval. |
| changes_requested | Reviewer requested plan changes. |
| rejected | Plan was rejected. |
| approved | Plan is approved and ready to execute. |
| in_progress | Experiment is currently executing. |
| result_pending_review | Result has been submitted for review. |
| result_changes_requested | Reviewer requested result changes. |
| completed | Result has been accepted. |
| archived | Experiment is closed and read-only. |
| cancelled | Experiment was cancelled before completion. |

## State Transitions

```text
draft -> pending_review
pending_review -> approved
pending_review -> changes_requested
pending_review -> rejected
changes_requested -> pending_review
approved -> in_progress
approved -> cancelled
in_progress -> result_pending_review
in_progress -> cancelled
result_pending_review -> completed
result_pending_review -> result_changes_requested
result_changes_requested -> result_pending_review
completed -> archived
```

## API Draft

The concrete framework is not selected yet. These endpoints define the module
contract and can be mapped to REST controllers, RPC handlers, or service
methods.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | /experiments | Search and filter experiments. |
| POST | /experiments | Create a draft experiment. |
| GET | /experiments/{id} | Get experiment details. |
| PATCH | /experiments/{id} | Update editable experiment fields. |
| POST | /experiments/{id}/submit | Submit a plan for approval. |
| POST | /experiments/{id}/approve | Approve a submitted plan. |
| POST | /experiments/{id}/request-changes | Request plan changes. |
| POST | /experiments/{id}/reject | Reject a submitted plan. |
| POST | /experiments/{id}/start | Start execution. |
| POST | /experiments/{id}/records | Add an execution record. |
| POST | /experiments/{id}/results | Submit experiment results. |
| POST | /experiments/{id}/results/approve | Accept submitted results. |
| POST | /experiments/{id}/archive | Archive a completed experiment. |
| GET | /experiments/{id}/audit-logs | View audit history. |

## Search and Filtering

Initial filters should include:

- code
- title keyword
- owner
- team
- status
- category
- priority
- planned date range
- actual date range
- safety level

Default sorting should prioritize recently updated experiments, with optional
sorting by planned start date, priority, and status.

## Permission Matrix

| Action | Researcher | Reviewer | Lab Manager | Administrator |
| --- | --- | --- | --- | --- |
| Create draft | Yes | Optional | Yes | Yes |
| Edit draft | Owner only | No | Yes | Yes |
| Submit plan | Owner only | No | Yes | Yes |
| Review plan | No | Yes | Yes | Yes |
| Start execution | Owner only | No | Yes | Yes |
| Add record | Owner or assigned member | No | Yes | Yes |
| Submit result | Owner only | No | Yes | Yes |
| Review result | No | Yes | Yes | Yes |
| Archive | No | No | Yes | Yes |
| View audit logs | Related users | Yes | Yes | Yes |

## Validation Rules

- Title, objective, category, owner, planned start time, and planned end time
  are required before submission.
- Planned end time must be later than planned start time.
- Protocol steps are required before submission.
- Only approved experiments can start execution.
- Execution records can only be added while an experiment is in progress.
- Results can only be submitted from the in-progress or
  result-changes-requested status.
- Archived experiments are read-only.
- Every status-changing operation must create an audit log entry.

## Integration Points

| Module | Integration Need |
| --- | --- |

| File storage | Protocol, record, and result attachments. |
| Notification | Approval reminders and status change notifications. |

## Suggested Implementation Slices

1. Domain and persistence
   - Experiment aggregate.
   - Protocol, record, result, and audit log persistence.
   - Status transition validation.
2. Basic workflow APIs
   - Draft creation and editing.
   - Submit, approve, reject, request changes, start, submit result, complete,
     archive.
3. Search and detail views
   - Paginated list with filters.
   - Detail endpoint including protocol, records, results, and audit logs.
4. Permission and audit hardening
   - Role checks.
   - Audit log coverage tests.
5. Attachments and integrations
   - File storage references.
   - Notification hooks.
   - Inventory and equipment references.

## Open Questions

- Which application stack and persistence technology will the project use?
- Does the business require formal electronic signatures or regulated audit
  trails?
- Are experiments single-team only, or can they span multiple teams?
- Should approval workflows be fixed, configurable by category, or delegated to
  an external workflow engine?
- Should experiment codes be globally sequential, team-scoped, or category
  scoped?
- Which attachment file types and size limits are allowed?
